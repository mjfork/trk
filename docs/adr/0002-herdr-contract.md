# The herdr contract is the CLI's JSON and a pull-only change feed

herdr's plugin (owned by the herdr-extension session) reads the tracker only through the CLI's JSON: `changes`, `show`, `ready`, `actors` and `claims`. It never opens the SQLite file. It learns about changes by polling `changes --since <seq> --json`, using an atomically rewritten `feed.head` file as a cheap hint. The tracker never calls herdr and stores no herdr ids. The only runtime identity the two share is the agent session id carried on claims. This narrows [ADR 0001](0001-own-store-not-beads.md): for herdr, the contract is the feed and the CLI's JSON, and the schema stays internal.

Agreed with herdr-extension on 2026-10-10, in the herdr plugin contract ticket.

## The contract

1. **Read interface.** CLI JSON only: `changes`, `show`, `ready`, `actors` (id, kind `human | agent`, display) and `claims` (live claims: session, actor, item, lease_until, taken_at). Asks and owners adds `roles` (role, actor, actor_kind, display) and `waiting` (open asks per resolved actor); ask rows already carry the resolved addressee, so neither is needed for routing. The plugin writes through the CLI like any other writer, as the registered agent role `herdr`. It only releases claims, sweeps leases and renews the claims of a session it shows idle, done or blocked (point 6; amended 2026-10-12, tr-2j4z7); it never writes item content. JSON Schemas for these replies live in `contract/`: `changes.schema.json`, `show.schema.json` and `ready.schema.json` (both built on `item.schema.json`, the item JSON every item read shares), `claims.schema.json`, `actors.schema.json` and `roles.schema.json`. `trk --version --json` (package version, the source tree's git commit, whether that tree is the installed trk, and the store schema; tr-b4jmn) is described by `version.schema.json`, so a consumer can cite the build it checked. Point 5's rule on adding fields applies to all of them.
2. **Feed.** `changes --since <seq> [--root <item>] [--limit N] --json` returns `{"schema":1,"epoch":E,"head":N,"changes":[…]}`, with rows in ascending seq. `--since` is exclusive. The journal is never compacted, so `--since 0` replays all history. The plugin keeps its own cursor, and that cursor is the pair (epoch, seq). There is no `--follow` mode.
   - **Epoch** (added 2026-10-11 with herdr-extension, tr-acf0s; additive, so `schema` stays 1). The store has an epoch, an opaque uuid set by `trk init`. Restoring a backup rewinds the journal, so its seqs are reused, and `trk restore` therefore rotates the epoch to a fresh uuid. A consumer whose stored epoch differs from the response's epoch, or whose cursor is above `head`, has read rows that were withdrawn: it drops what it built from the feed and rebuilds from `--since 0`. Checking `head` alone is not enough. A consumer that was down during a restore may poll only after the new head has passed its cursor again, and would silently skip the reused seqs. The store is restored only with `trk restore`, never by copying files: a backup carries the old epoch, so a plain copy cannot be detected.
3. **seq.** A strictly increasing integer in commit order. It is not gapless.
4. **Rows.** Each row has: seq, at (UTC), change, item, kind, form, title, parent, root, depth (after the change), actor, session, owner (the effective owner after the change), status_old, status_new and data. Ask rows add addressee.

   - Ownership: `owner.changed`.
   - Claims: `claim.taken`, `claim.renewed`, `claim.released`, `claim.expired`.

6. **Leases.** Every CLI invocation first sweeps lapsed leases and journals `claim.expired` for each, with `at` set to the expiry time. Renewing a lease is the claimant's job: the agent renews its own lease from a zero-token per-turn hook (`claim renew --session $SESSION`), so a hung agent's lease lapses on its own. On pane exit or session end the plugin runs `claim release --session S` for each of that session's claims.
   - **herdr renews for a waiting session** (amended 2026-10-12, tr-2j4z7; Michael ruled it in place of "the plugin never renews a lease"). An idle session takes no turns, so its hook never fires and its claims lapsed after the lease; waking it to renew re-sends its whole context. The plugin, writing as `herdr`, may run `claim renew --session S` for a session only while herdr reports that session's agent as `idle`, `done` or `blocked` (ready for input, or waiting at an approval dialog on a person). It never renews a session herdr reports as `working` (that session renews itself through its hook, and one stuck working is hung and must lapse) or `unknown`, nor one whose pane is gone. The `claim.renewed` row carries actor `herdr` and the claimant's session S; the claim's own actor is unchanged. So a session left waiting keeps its claims while its pane lives, and pane exit or session end still releases them. No CLI, schema or feed change: any actor could already run `claim renew --session S`.
7. **Wake hint.** After each commit the CLI rewrites `<store dir>/feed.head` (the latest seq) atomically, by writing a temp file and renaming it. `trk restore` rewrites it too, so it can go backwards. Polling stays the contract.
8. **Session id.** A claim's session is the Claude session uuid, opaque to the tracker. Compaction and `--resume` keep it. `/clear` mints a new one, so the old claim lapses and the agent must claim again. The plugin keeps workspace, tab and pane ids in its own runtime binding, keyed never on pane id. The tracker keeps no runtime-binding record, and pages derive "live" from claims.
9. **Placement is plugin policy.** Rows carry root and depth. The plugin's *default* placement:
   - depth 0 → a Space;
   - depth 1 → a tab;
   - depth 2 or more → a pane in the nearest ancestor that has a tab.

   The orchestrator may promote any claimed item to its own tab.
10. **Ask routing** (the plugin's rule; Asks and owners finishes the row fields).
    - A human addressee is reached through plugin-defined channels, keyed by actor id in the plugin's config. The tracker knows nothing about channels.
    - For an agent-role addressee, the plugin tries in order:
      1. that role's live claim on the ask's nearest ancestor;
      2. otherwise the orchestrator of the root's Space, which the plugin resolves from its own runtime binding (it may or may not hold a claim, since a program root is never claimed from the frontier);
      3. otherwise it escalates through the root owner's channels.
    - `ask.answered` carries owner (the parent's effective owner) and data.parent_claim_session. The plugin wakes that session if it is live, and otherwise notifies the owner.

## Considered options

- **The plugin reads SQLite directly.** This is faster, but it would freeze the schema as a public interface and couple herdr to our migrations.
- **The tracker pushes to herdr** (calls the herdr CLI after a commit, or runs a daemon). This makes the tracker depend on herdr, adds a daemon, and still needs a cursor for missed events.
- **A blocking `changes --follow`.** It pins a Python process per watcher; `feed.head` with stat or inotify gives the same latency.
- **The plugin renews leases for agents that look alive.** A hung but live pane would hold its claim forever.
  - Still rejected as stated (annotated 2026-10-12, tr-2j4z7). Point 6's narrowed rule answers it: herdr renews only a session it shows `idle`, `done` or `blocked`, never one that is `working` or `unknown` or whose pane is gone. A hung session shows `working` or `unknown`, so herdr never renews it and its lease still lapses on its own.
- **A tracker-side runtime-binding record.** It would put herdr ids in the tracker; claims already say what is live.

## Consequences

- The Core store + CLI spec carries this as its Change feed section, together with `actors`, `claims`, `claim renew/release` and `sweep`.
- Asks and owners must stay within the ask row shape and the reserved names.
- Where the build discipline is enforced can use the plugin as an enforcement point, since the plugin reads `ready` and item form before it starts a worker.
- Not part of the contract: the plugin's internals, whether every open top-level item gets a Space automatically (Michael is deciding that on the plugin side), and multiple writers.
