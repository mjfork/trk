# Agents in this repo

## Working from trk

Work is tracked in the machine-wide `trk` store (`~/.local/share/trk/`), not in `.scratch/` markdown. The Tracker v1 program is `tr-yk91p`, the top-level item `trk tree` shows; vocabulary is `CONTEXT.md`. Pass `--json` to any verb for the shared item shape.

- **Find work:** `trk ready --root <program>` lists what you can start now, urgent first, then in tree order. `trk show <id>` says why an item is not ready (`why_not`).
- **Take it:** `trk claim <id>`, or `trk claim --next --root <program>`. Claims need your Claude session uuid. The session hooks in `hooks/` export it as `$TRK_SESSION` and renew your lease every turn. Without them, pass `--session <uuid>` and run `trk claim renew --session <uuid>` yourself. A claim that lapses is gone, so claim again after `/clear`.
- **Write the body:** `trk section set <id> <handle> --file F` (stdin by default), for example `what-to-build` or `resolution`. `trk section get <id> <handle>` reads one section.
- **Criteria:** acceptance criteria (and a program's destination) are rows, not a written section: `trk criterion add <id> "<one line>"`, `trk criterion edit <id> ac-<n> "<text>"`, `trk criterion retire <id> ac-<n> --reason "…"`, and `trk criteria <id>` lists them. The `acceptance-criteria` and `destination` sections are generated from them.
- **Prove it:** `trk evidence add <id> --kind pr|test-run|merge|judgment|review|… --gate <gate> [--criterion ac-<n>] [--ref R] [--sha S] [--verdict pass|fail] --note "<one line>"` records a never-edited evidence row; `trk evidence retract <id> <evidence-id> --note "<why>"` withdraws one; `trk evidence <id>` lists them with whether each counts. `trk advance <id>` moves a ticket one stage forward and refuses with the missing list otherwise: Built needs a `pr` row at the head sha and a passing `test-run` at that sha; Merged needs Built still at the head, a `merge` row and a `trk blast-radius <id>` rating at the head (GREEN merges unreviewed; YELLOW and RED need an independent `audit`, a latest independent verdict on every ledger row and every RISKY, WRONG, confirmed reward-hack and contradiction row settled, see Log your forks; RED also needs a person's approval at the head sha, recorded with `trk review record <id> approved --sha <head> --note "…" --as <person>`, which answers the RED-read ask `blast-radius` opened to `engineering`; it needs no GitHub, and `--ref <review URL>` records a GitHub review instead). This repo's lanes are set in `.trk/blast-radius`. After a fast-forward merge, rate with `trk blast-radius <id> --base <the commit you branched from>`; Verified needs a passing `verified` run per live criterion at a sha containing the merge sha. `--judgment "<note>"` judges a self-contained ticket at framed complete. `trk show <id>` names the next gate and what it lacks. `trk reopen-stage <id> <stage> --reason "…"` moves an open ticket back, and the gates above that stage then count only evidence recorded after the move (`before-reopen` otherwise); reopening a ticket closed at Verified needs `trk reopen <id> --to-stage <stage> --reason "…"`. A ticket that changes no repo records `pr --ref none` and skips Merged with `trk skip <id> merged --reason "…"`.
- **Log your forks:** while building, `trk ledger add <id> --kind fork --decided "…" --alternative "…" --why "…"` logs each correctness-relevant fork as `ledger-<n>` (`contradiction` takes `--conflicts-with <ADR or spec:<section>>`); a correction is a new row with `--refers-to <n>`. Settle a judged row with `trk ledger settle <id> <n> fixed --sha <fix>` (it counts once an independent session re-checks it SOUND, or REFUTED for a flag), `deferred` (files a self-contained ticket for it), or `accepted --ask <A> [--adr PATH]` / `overruled --ask <A>`, where A is an `engineering` ask tied to the row (`trk ask <id> --to engineering --ledger <n> …`) that a person answered; the builder never writes those two, nor defers its own row. A confirmed reward-hacking flag is only fixed. `trk ledger list <id>` shows the rows. An auditor (`ledger add --origin auditor`, `ledger audit`) and a reviewer (`ledger verdict <id> <n> sound|risky|wrong --note "…"`) must work from a session that never built the ticket, or the tracker refuses them `not-independent`. Tie an ask to a row with `trk ask <id> --to engineering --ledger <n> …`. An auditor row with `--repeat-of <ticket>:<n> --topic "…"` relates both tickets to a `Ticket template: add a field for <topic>` ticket under `trk config` `template-parent`, filing it if none is open.
- **Specs:** `trk spec accept <project>` needs every spec section written, a live criterion and a `judgment` row for gate `accept` (its actor is the acceptor); it moves the project's Framed tickets to Spec'd. `trk spec draft <project> --reason "<one line>"` moves its Spec'd tickets back to Framed.
- **Wire it:** `trk link <a> blocks <b>` means b waits on a. `relates` and `supersedes` are the other edge types, and `trk unlink` removes an edge.
- **Ask, don't stop:** when you need someone to decide something before you can go on, open an ask instead of ending your turn with "Needs you": `trk ask <id> --to product|engineering|parent "<question>" --question -` (the body on stdin). The ask keeps `<id>` off the frontier until it is answered, and herdr routes it to whoever holds the role. `trk waiting` lists the open asks waiting on you (`--me <actor>`, `--all`). `trk answer <ask> --outcome "<gist>" --answer -` answers one; `trk withdraw <ask> --reason "<why>"` drops one you no longer need.
- **Finish:** a ticket closes `done` only by reaching Verified: `trk advance <id> --outcome "<one sentence>"` from merged (`close --resolution done` on a ticket is refused, `done-needs-verified`). Other items close with `trk close <id> --resolution done --outcome "<one sentence>"`. Children close first, and a close is refused (`open-asks`) while the item or a descendant has an open ask: answer each or `trk withdraw` it on purpose (Michael's ruling tr-29kgp, 2026-10-22: "Refuse to close until each open question is answered or withdrawn on purpose"). Put the full resolution text, with the commit sha, in the `resolution` section before closing. Closing ends your claim. A project or program closes `done` only when every live criterion has a passing `close` row (a run, or `--kind judgment --gate close --criterion ac-<n>` citing what delivered it), and a decision only with its `resolution` written.
- **New work:** `trk new work-item "<title>" --form spec-bound|self-contained|decision [--subtype …] --parent <id>`. A ticket is refused unless it comes with its written sections (`--section what-to-build=@F`, or `current-behaviour` and `desired-behaviour` for a self-contained one) and at least one `--criterion "<text>"`; a program needs one `--criterion` too. Each ticket has a stage (`framed`, then `specd` once its project's spec is accepted).

Write as yourself with `--as <actor>` or `$TRK_ACTOR`; `trk actors` lists who is registered. Tests never touch the real store: the suite forces a temp `$TRK_HOME`.

Restore the store only with `trk restore <backup>`, never by copying files. It rotates the store's epoch, which is how feed consumers such as herdr learn that the journal rewound (ADR 0002 point 2).

Never run trk from a worktree or second checkout without an explicit `$TRK_HOME`: use plain `trk …` for the live store (trk prints `trk: store <path> (from $TRK_HOME)` on stderr whenever `$TRK_HOME` is set, so a stray export is visible), and `TRK_HOME=<tmp> TRK_TEST=1` on the same command line for worktree code. A worktree build that migrated the live store once locked every installed build out with `schema-newer`. trk now refuses (exit 1, rule `foreign-build`) to migrate or create the default store from any source tree but the one `uv tool install` installed. The main checkout is that tree, so keep it on master: an unmerged branch checked out there can still migrate the live store.

The installed `trk` is an editable install of this checkout's `src/`: a fast-forward of master is live for every session at once, with no reinstall (`trk --version` shows the commit).

Several builds share this machine and run pytest at the same time. Never stop a process by pattern (`pkill -f`, `killall`): on 2026-10-11 four sessions' `pkill -f "pytest -q …"` killed each other's suites. Stop only your own process, by the PID you started, and run long suites detached (`setsid`) so they survive your shell. One build merges at a time: when master moves, rebase and rerun before you fast-forward.
